# Правила TaskServiceAPI

Это задел на будущее ASP.NET Core 10 API для задач, проектов и рабочих
пространств. Первый релиз TaskFlow полностью локальный и не использует этот
проект. Общие правила находятся в корневом `AGENTS.md`.

- На серверном этапе каждая задача будет принадлежать рабочему
  пространству/проекту и иметь стабильный
  идентификатор. Контролируйте доступ через владельца и роль текущего субъекта;
  одного `TaskId` недостаточно.
- Статус — ограниченный набор значений домена. Не принимайте произвольную
  строку из клиента и не разрешайте переходы, противоречащие правилам продукта,
  без явно согласованного workflow.
- Разделяйте входные команды, доменные модели и выходные DTO. Не сериализуйте
  сущности хранения напрямую.
- Создание и изменение должны быть идемпотентны там, где клиент может повторить
  запрос. Учитывайте конкурентное изменение, сортировку и пагинацию при выдаче
  списков.
- Сроки и временные метки храните в UTC, а часовую зону учитывайте на границе
  UI. Ограничивайте длину заголовка/описания и проверяйте даты на сервере.
- Не возвращайте задачи другого профиля или workspace даже при ручной подмене
  идентификатора в URL. Это обязательный негативный тест.
- Контроллеры не должны содержать файловую/базовую логику и сложные правила
  статусов. Подготовьте сервисный слой до добавления нескольких endpoint-ов.
- Публичные endpoint-ы документируйте через OpenAPI: request/response, ошибки,
  авторизацию, фильтры и пагинацию.

Проверка:

```powershell
dotnet build TaskServiceAPI
dotnet run --project TaskServiceAPI
```

Для каждой операции проверьте успешный сценарий, валидацию, повтор запроса,
неверный статус, несуществующий ID и попытку доступа к чужому workspace.
