# Правила IdentityServiceAPI

Это задел на будущее ASP.NET Core 10 API для идентичности и профилей. Первый
релиз TaskFlow полностью локальный и не использует этот проект. Общие правила
находятся в корневом `AGENTS.md`.

- Здесь могут появиться аккаунты/профили, регистрация, вход, сессии и
  авторизация на отдельном серверном этапе. Логику задач и проектов сюда не
  добавляйте.
- Не подключайте этот API к локальному MVP и не добавляйте сетевую зависимость
  только ради демонстрации. Локальный профиль не называйте аккаунтом и не
  добавляйте фиктивную проверку пароля.
- Контроллеры должны быть тонкими: валидация транспорта, вызов сервиса,
  корректный HTTP-ответ. Хранилище, хеширование, токены и правила доступа — в
  отдельных сервисах.
- Никогда не возвращайте пароль, секрет, refresh token или внутренние поля
  хранения в DTO/логи. Пароли при появлении серверной аутентификации хранятся
  только как стойкие хеши, а секреты берутся из конфигурации окружения/секретов.
- Нормализуйте и валидируйте уникальные идентификаторы и email на сервере.
  Ошибки конфликта возвращайте предсказуемо (`409`), ошибки валидации — `400`,
  отсутствие аутентификации — `401`, отсутствие прав — `403`.
- Не меняйте публичный контракт без обновления документации, DTO и тестов.
  Для breaking changes используйте версию API или согласованный migration plan.

Проверка:

```powershell
dotnet build IdentityServiceAPI
dotnet run --project IdentityServiceAPI
```

Проверьте регистрацию/вход, невалидные данные, повторную регистрацию,
неавторизованный доступ и то, что секреты отсутствуют в ответах и логах.
