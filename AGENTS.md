# TaskFlow System — правила проекта

## Назначение продукта

TaskFlow System — полностью локальное и офлайн-доступное настольное приложение
для управления задачами. Основной пользовательский сценарий: пользователь
выбирает профиль, открывает рабочее пространство и создаёт/изменяет задачи на
канбан-доске. Интерфейс должен быть понятным, быстрым и визуально
последовательным.

Текущий репозиторий находится в переходном состоянии: WPF-клиент уже содержит
локальные профили и демонстрационный экран доски, а `IdentityServiceAPI` и
`TaskServiceAPI` пока являются стартовыми ASP.NET Core-проектами. Первый релиз
не зависит от этих API. Не выдавайте макет или `MessageBox` за готовую
бизнес-функцию.

## Приоритеты продукта

1. Корректность данных и изоляция данных профилей.
2. Понятный пользовательский сценарий создания, редактирования и завершения
   задачи.
3. Согласованный и доступный интерфейс.
4. Автономная работа и сохранность локальных данных.
5. Простота поддержки и небольшие, проверяемые изменения.
6. Дополнительные представления (список, календарь, таймлайн), отчёты и
   коммерческие функции — только после надёжного MVP.

## Архитектурные границы

- `TaskFlowSystem/` — WPF-клиент на .NET Framework 4.7.2. Не используйте API,
  доступные только в современном .NET, без явной проверки совместимости.
- `IdentityServiceAPI/` — задел на будущую серверную идентификацию; не является
  частью локального MVP.
- `TaskServiceAPI/` — задел на будущую серверную работу; не является частью
  локального MVP.
- Не смешивайте UI, HTTP, хранение и бизнес-правила в одном обработчике.
  Если слой ещё не выделен, добавляйте его постепенно и не делайте большой
  рефакторинг частью несвязанной задачи.
- Общие DTO и контракты должны быть явно версионируемыми. Не подключайте один
  проект к внутренним классам другого API только ради повторного использования.
- Локальный режим и серверный режим — разные режимы хранения. Нельзя молча
  смешивать локальные профили из `%APPDATA%` с удалёнными аккаунтами.

## Утверждённая модель первого релиза

- Приложение полностью локальное и работает без интернета.
- Профиль — локальное имя пользователя без пароля, регистрации аккаунта,
  восстановления доступа и входа с другого компьютера. Профиль не является
  механизмом безопасности.
- Профили изолируются стабильным `LocalProfile.Id`, а не отображаемым именем.
- Задачи, проекты, комментарии, история изменений и метаданные хранятся на
  компьютере пользователя. Формат и расположение хранилища должны быть
  определены до реализации задач.
- У задачи обязательны название, статус, срок выполнения и описание.
- Комментарии, вложения, теги и история изменений входят в продуктовую модель,
  но могут быть реализованы после базового CRUD задач, если это нужно для
  управляемого MVP.
- Поддерживаются личные и общие задачи. Правило определения видимости общей
  задачи должно быть явно утверждено до реализации совместного режима; наличие
  профиля само по себе не определяет права доступа.
- Роли администратора, менеджера и участника не вводятся.

### Приоритет реализации локального MVP

1. Локальное хранилище и модель задачи.
2. Создание, просмотр, редактирование, удаление/архивирование и перемещение
   задач по статусам.
3. Валидация обязательных полей и сохранение после перезапуска.
4. Личные и общие задачи после утверждения правила их видимости.
5. Комментарии, вложения, теги и история изменений.
6. Поиск и фильтры по задачам.

Порядок допускает технические перестановки, но создание и надёжное сохранение
задач имеют приоритет над поиском, фильтрами, календарём и отчётами.

Не смешивайте будущую серверную синхронизацию с локальным MVP. Если позднее
появится серверная архитектура, это будет отдельный этап с собственной моделью
аккаунтов, авторизации, хранения и миграции. Не храните пароли или токены в
репозитории, исходниках, `appsettings*.json` или логах.

## Правила реализации

### Общие

- Сначала изучите существующий код и локальные `AGENTS.md`; более глубокое
  правило имеет приоритет над этим файлом.
- Делайте изменения атомарными: одна задача — одна понятная причина изменения.
  Не переписывайте весь экран или архитектуру без необходимости.
- Сохраняйте текущую кодировку и язык интерфейса. Текущий UI русскоязычный;
  новые пользовательские строки пишите на русском и не оставляйте отладочные
  сообщения в финальном сценарии.
- Используйте явные имена, небольшие методы и проверку входных данных на границе
  системы. Не глотайте исключения без объяснения, безопасного fallback и
  диагностируемого логирования.
- Для сущностей с идентификаторами не полагайтесь на имя или отображаемый текст.
  Даты, создаваемые на сервере или сохраняемые между процессами, храните в UTC.
- Не добавляйте зависимости без необходимости. При добавлении пакета объясните
  его назначение и совместимость с целевым фреймворком.

### Данные и безопасность

- Для каждой операции с задачей проверяйте профиль/область видимости и
  принадлежность данных, а не только наличие `TaskId`. Даже в локальном
  приложении нельзя смешивать личные данные разных профилей.
- Не доверяйте значениям, пришедшим из клиента: статусам, идентификаторам,
  ролям, срокам и текстовым полям. Ограничения должны быть и на клиенте для UX,
  и на сервере для безопасности.
- Не удаляйте данные без подтверждения и продуманного поведения активного
  профиля. Для важных удалений предпочтительнее архивирование/soft delete.
- Запись JSON, SQLite или другого локального состояния должна переживать
  неполную запись: временный файл, атомарная замена и восстановление из
  резервной копии — по мере роста критичности данных. Пользователь не должен
  терять задачи из-за сбоя во время сохранения.

### UI/UX

- Сохраняйте тёмную зелёную визуальную систему и общие ресурсы из `Theme.xaml`
  и `MainWindow.xaml`; не вводите случайные фиолетовые/синие цвета в новых
  компонентах.
- Любое действие должно иметь состояние loading/disabled, успех и понятную
  ошибку. `MessageBox` допустим для прототипа или критического подтверждения,
  но не как замена рабочему экрану, форме или валидации.
- Навигация, клавиатура, фокус и контраст важны не меньше внешнего вида.
  Интерактивные элементы должны иметь доступное имя, tooltip там, где смысл не
  очевиден, и визуальное состояние hover/pressed/disabled.
- Не показывайте пустые декоративные представления как готовую функцию:
  используйте честные empty/loading/error states.
- Не меняйте тексты и визуальную палитру массово в задаче, посвящённой данным,
  если это не требуется для сценария.

## Работа с ветками и изменениями

- Работайте только в своей ветке. Не переписывайте историю и не меняйте чужие
  незакоммиченные изменения.
- Перед началом проверьте `git status` и после работы повторите его.
- Название ветки должно кратко описывать задачу, например
  `feature/task-create` или `fix/profile-storage`.
- Коммит должен быть небольшим и содержать одну логическую часть работы.
  Не коммитьте `bin/`, `obj/`, `.vs/`, пользовательские файлы и секреты.
- В описании PR укажите: цель, изменённые проекты, способ проверки, ограничения
  и известные риски. Для UI добавьте скриншот или короткое видео.

## Проверка перед завершением задачи

Минимальный набор проверок зависит от затронутого слоя:

```powershell
dotnet build IdentityServiceAPI
dotnet build TaskServiceAPI
```

Для WPF-клиента соберите `TaskFlowSystem\\TaskFlowSystem.csproj` через Visual
Studio/MSBuild с установленным .NET Framework 4.7.2. Если локальная среда не
позволяет выполнить сборку, укажите это явно.

Также проверьте вручную затронутый сценарий: первый запуск, создание профиля,
переключение и удаление профиля; для задач — создание с обязательными полями,
редактирование, перемещение, поиск, фильтры, комментарии, вложения, историю,
отмену и ошибку сохранения. Отдельно проверьте работу после перезапуска и без
интернета. API проверяйте только в задачах, которые явно относятся к будущему
серверному этапу.

## Приёмка функциональной задачи

Перед реализацией сформулируйте:

1. кто пользователь и какой сценарий он выполняет;
2. какие данные создаются и кому принадлежат;
3. что происходит при отмене, повторном запросе, пустом состоянии и ошибке;
4. как функция работает после перезапуска и без сети;
5. как её проверить автоматически или вручную.

Если пункт нельзя определить из задачи, задайте вопрос или зафиксируйте
допущение в PR. Не принимайте решение о безопасности или модели данных молча.
